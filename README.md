# Distributed Search Pipeline

Розподілена система повнотекстового пошуку з паралельною побудовою інвертованого індексу та інтеграцією локальної великої мовної моделі (LLM Ollama) для семантичного розширення пошукових запитів (Query Expansion).

Курсова робота з дисципліни "Паралельні обчислення".  
Національний технічний університет України "Київський політехнічний інститут імені Ігоря Сікорського"  
Навчально-науковий інститут прикладного системного аналізу (НН ІПСА), кафедра системного проектування (СП).

## Архітектура та технологічний стек

Система реалізує клієнт-серверний пайплайн із розподілом обчислень між компонентами:

- **Search Server (Backend)**: Java 21, Spring Boot 3, Maven.
  - **Власний пул потоків (ThreadPool)**: реалізований без використання високорівневих утиліт `java.util.concurrent.ExecutorService`. Працює на базі власної потокобезпечної блокуючої черги задач (`ThreadSafeTaskQueue`) з механізмом `wait`/`notifyAll`.
  - **Власна потокобезпечна структура індексу**: комбінація хеш-таблиці `CustomHashMap` та потокобезпечних списків входжень `ConcurrentPostingList` із блокуваннями на рівні записів для запобігання стану гонки (race conditions) при паралельній індексації.
  - **Пошуковий рушій**: повнотекстовий пошук за ключовими словами (`keyword search`) та збагачений запит через LLM (`expanded search`) із ранжуванням результатів за релевантністю (score).
  - **WebSocket Handler**: стрімінг проміжних стадій обробки запиту клієнту в реальному часі.
- **LLM Engine (Query Expansion)**: локальний сервер Ollama з моделлю `llama3.2:1b`, що генерує релевантні ключові слова та комерційні синоніми через REST API `/api/generate`.
- **Клієнти**:
  - **Web Client**: чистий інтерфейс (HTML5, modern CSS, ванільний JavaScript) із вибором режиму пошуку, стрімінгом пайплайну через WebSocket та переглядом вихідного JSON-документа.
  - **CLI Clients**: консольні клієнти на Python 3 (`search.py`, `index.py`) з підтримкою аргументів командного рядка (`--mode`, `--raw`, `--top`, `--threads`, `--benchmark`) та інтерактивного термінального режиму.
- **Контейнеризація**: Docker Compose об'єднує сервіси `search-server` та `ollama` у спільній ізольованій мережі.

## Вимоги до системного оточення

Для запуску системи необхідні такі встановлені компоненти:

- **Docker** версії 24.0+ та **Docker Compose** v2+.
- **Python** версії 3.10+ (використовується для скрипта нарізки датасету, CLI-клієнтів та запуску бенчмарків).
- **Оперативна пам'ять**: не менше 8 ГБ (рекомендовано 16 ГБ, оскільки JVM-процесу виділено 6 ГБ через `-Xmx6g`, а контейнеру Ollama потрібно близько 1.5–2 ГБ).
- **JDK 21** та **Maven 3.9+** потрібні лише у разі запуску чи тестування бекенда локально без Docker.

## Швидкий запуск (Docker Compose)

Усі основні сервіси розгортаються за допомогою однієї команди:

### 1. Підняття контейнерів

```bash
docker compose up -d
```

Команда автоматично збере образ бекенда `search-server` (на базі Eclipse Temurin 21) та запустить сервіси `search-server` (порт 8080) і `ollama` (порт 11434).

### 2. Завантаження моделі в Ollama (лише при першому запуску)

Модель зберігається у Docker volume `ollama-data`, тому завантажується один раз:

```bash
docker exec -it ollama ollama pull llama3.2:1b
```

### 3. Перевірка працездатності (Health Check)

```bash
curl http://localhost:8080/api/health
```

Очікувана відповідь (HTTP 200 OK):

```json
{"status":"ok","ollama":true}
```

## Датасет: джерело, нарізка та підготовка

### 1. Джерело датасету

Згідно з вимогами силабусу, для роботи системи необхідний текстовий набір документів англійською мовою обсягом не менше 1 ГБ та не менше 10 000 документів.

У проєкті використано офіційний датасет **Amazon Reviews 2023**:
- Репозиторій: https://amazon-reviews-2023.github.io/index.html
- Категорія: `Health_and_Household`
- Тип завантаження: **meta** (метадані товарів: `title`, `description`, `features`, `store`)
- Назва завантаженого файлу: `meta_Health_and_Household.jsonl`

### 2. Структура директорій даних

```
data/
  raw/          # Папка для вихідного завантаженого .jsonl файлу
  batched/      # Папка для нарізаних батчів, які монтуються в Docker-контейнер
```

*Примітка:* Директорія `data/` включена у `.gitignore`, тому самі великі файли даних не зберігаються в репозиторії Git.

### 3. Встановлення Python-залежностей

Створіть та активуйте віртуальне оточення:

```bash
# Створення venv
python -m venv .venv

# Активація у Windows PowerShell:
.\.venv\Scripts\Activate.ps1

# Активація у Linux / macOS:
source .venv/bin/activate

# Встановлення необхідних бібліотек
pip install -r requirements.txt
```

Файл `requirements.txt` містить залежності:
- `requests>=2.31.0` — HTTP-запити для тестувальних скриптів;
- `matplotlib>=3.8.0` — візуалізація та генерація графіків масштабованості;
- `locust>=2.24.0` — стрес-тестування системи під навантаженням.

### 4. Нарізка датасету на паралельні батчі

Для забезпечення ефективного читання та багатопотокової індексації великий сирий файл нарізається на фрагменти за допомогою скрипта `scripts/slice_dataset.py`:

```bash
python scripts/slice_dataset.py --input data/raw --output data/batched --batch-size 5000 --max-docs 400000
```

Скрипт автоматично виявляє файли `.jsonl` у вказаній вхідній папці (або приймає прямий шлях до окремого файлу).

**Параметри `scripts/slice_dataset.py`:**
- `--input`, `-i`: шлях до сирого файлу `.jsonl` або каталогу з файлами (за замовчуванням `data/raw`);
- `--output`, `-o`: каталог для збереження нарізаних файлів `batch_XXXX.jsonl` (за замовчуванням `data/batched`);
- `--batch-size`, `-b`: кількість JSON-документів в одному батч-файлі (за замовчуванням `5000`);
- `--max-docs`, `-m`: максимальна кількість документів для обробки (за замовчуванням `400000`, значення `0` означає обробку всього файлу без обмежень);
- `--start-batch`: початковий індекс нумерації батчів (за замовчуванням `1`).

У результаті виконання у папці `data/batched/` утворюється 80 файлів загальним обсягом 1.32 ГБ (400 000 повнотекстових документів), що монтуються в контейнер за шляхом `/app/data/batched`.

## Побудова індексу (Індексація)

Після запуску контейнера інвертований індекс знаходиться у пам'яті сервера. Для побудови індексу необхідно ініціювати паралельний процес індексації.

### Варіант 1: Через CLI-клієнт

```bash
python cli-client/index.py --threads 12
```

### Варіант 2: Через cURL

```bash
curl -X POST http://localhost:8080/api/index \
  -H "Content-Type: application/json" \
  -d '{"threads": 12}'
```

Очікувана відповідь сервера:

```json
{
  "status": "ok",
  "documents_indexed": 400000,
  "time_ms": 19771
}
```

### Перевірка поточного стану індексу

```bash
curl http://localhost:8080/api/stats
```

Відповідь:

```json
{
  "documents": 400000,
  "index_build_time_ms": 19771,
  "threads_used": 12
}
```

## Використання клієнтів

Система надає два незалежних клієнтських інтерфейси згідно з вимогами завдання.

### Веб-клієнт (Web UI)

Веб-інтерфейс реалізований як статичний клієнт без сторонніх залежностей.

1. Відкрийте файл `web-client/index.html` у браузері (подвійним кліком або перетягуванням у вікно браузера).
2. Можливості веб-інтерфейсу:
   - **Вибір режиму пошуку**: перемикач між **Keyword** (швидкий пошук за індексом) та **Expanded** (збагачення запиту через Ollama).
   - **WebSocket-стрімінг**: відображення живого статусу виконання пайплайну в реальному часі (з'єднання з сокетом $\to$ генерація синонімів через Ollama $\to$ сканування індексу $\to$ фінальний результат).
   - **Картки результатів**: показ релевантності (Score), назви товару, ідентифікатора документа та кнопки "View raw product JSON" для перегляду повного оригінального документа з датасету.
   - **Панель індексації**: можливість запустити перебудову індексу з вказанням кількості потоків (від 1 до 128) прямо з інтерфейсу.

### Консольний пошук (CLI Search)

Скрипт `cli-client/search.py` реалізує клієнт повнотекстового пошуку через термінал:

**Одиночний пошуковий запит у режимі keyword:**

```bash
python cli-client/search.py "protein powder vanilla" --mode keyword --top 5
```

**Пошук із розширенням через Ollama та переглядом вихідного JSON:**

```bash
python cli-client/search.py "vitamin c serum" --mode expanded --raw
```

**Інтерактивний режим:**

```bash
python cli-client/search.py --mode keyword
```

У цьому режимі користувач може вводити запити послідовно. Для виходу достатньо ввести `exit` або натиснути `Ctrl+C`.

**Параметри `cli-client/search.py`:**
- `query`: текстовий пошуковий запит (якщо не вказано — запускається інтерактивний режим);
- `--mode`, `-m`: режим пошуку: `keyword` або `expanded` (за замовчуванням `keyword`);
- `--top`, `-k`: кількість результатів у вибірці (за замовчуванням `5`);
- `--raw`, `-r`: відображати повний сирий JSON документа з диска;
- `--url`: адреса ендпоінту пошуку (за замовчуванням `http://localhost:8080/api/search`);
- `--stats-url`: адреса ендпоінту статистики (за замовчуванням `http://localhost:8080/api/stats`).

### Консольне керування індексом (CLI Index)

Скрипт `cli-client/index.py` забезпечує керування та аналіз процесу побудови індексу:

**Перевірка стану сервера та індексу:**

```bash
python cli-client/index.py --status
```

**Паралельна побудова індексу з фіксацією потоків:**

```bash
python cli-client/index.py --threads 12 --force
```

**Бенчмаркінг індексації при різній кількості потоків із збереженням у CSV:**

```bash
python cli-client/index.py --benchmark 1 2 4 8 12 16 32 --output benchmarks/results/index_speedup.csv
```

## Специфікація API

### REST API

Усі відповіді повертаються у форматі JSON з HTTP-кодом 200 при успішній обробці.

#### Зведена таблиця ендпоінтів

| Метод | Ендпоінт | Тіло запиту | Тіло відповіді | Опис |
|---|---|---|---|---|
| `GET` | `/api/health` | Відсутнє | `{"status": "ok", "ollama": true}` | Перевірка працездатності пошукового сервера та зв'язку з контейнером Ollama |
| `POST` | `/api/index` | `{"threads": 8}` | `{"status": "ok", "documents_indexed": 400000, "time_ms": 23412}` | Запуск паралельної побудови індексу пулом із вказаної кількості потоків |
| `GET` | `/api/stats` | Відсутнє | `{"documents": 400000, "index_build_time_ms": 19771, "threads_used": 12}` | Отримання статистики поточної копії індексу у пам'яті |
| `POST` | `/api/search` | `{"query": "organic tea", "mode": "keyword", "top": 5}` | `{"results": [{"doc_id": "...", "score": 14.2, "snippet": "...", "raw": {...}}], "time_ms": 4.2, "synonyms": [...]}` | Пошук документів у режимі `keyword` або `expanded` із Min-Heap ранжуванням |

#### Детальний опис полів та типів даних

##### 1. `GET /api/health`
Перевірка доступності пошукового сервісу та зовнішнього контейнера Ollama.
* **Тіло запиту**: відсутнє.
* **Тіло відповіді (JSON Object)**:
  | Поле | Тип | Опис |
  |---|---|---|
  | `status` | `String` | Статус працездатності бекенду (значення `"ok"`). |
  | `ollama` | `Boolean` | `true`, якщо Ollama доступна за адресою `OLLAMA_BASE_URL`; інакше `false`. |

##### 2. `POST /api/index`
Ініціалізація паралельної індексації датасету власним пулом потоків.
* **Тіло запиту (JSON Object)**:
  | Поле | Тип | Обов'язкове | Опис |
  |---|---|:---:|---|
  | `threads` | `Integer` | Ні | Кількість робочих потоків у пулі. За замовчуванням: кількість логічних ядер процесора. |
* **Тіло відповіді (JSON Object)**:
  | Поле | Тип | Опис |
  |---|---|---|
  | `status` | `String` | Результат операції (`"ok"`). |
  | `documents_indexed` | `Integer` | Загальна кількість успішно розпарсених та проіндексованих документів. |
  | `time_ms` | `Long` | Час повної паралельної побудови індексу в мілісекундах. |

##### 3. `GET /api/stats`
Отримання метрик стану інвертованого індексу в оперативній пам'яті.
* **Тіло запиту**: відсутнє.
* **Тіло відповіді (JSON Object)**:
  | Поле | Тип | Опис |
  |---|---|---|
  | `documents` | `Integer` | Поточна кількість документів в активному індексі. |
  | `index_build_time_ms` | `Long` | Час останньої побудови індексу в мілісекундах. |
  | `threads_used` | `Integer` | Кількість потоків пулу, яка використовувалась при останній індексації. |

##### 4. `POST /api/search`
Повнотекстовий пошук за ключовими словами або розширений семантичний пошук через LLM.
* **Тіло запиту (JSON Object)**:
  | Поле | Тип | Обов'язкове | Опис |
  |---|---|:---:|---|
  | `query` | `String` | Так | Текст пошукового запиту. |
  | `mode` | `String` | Ні | Режим пошуку: `"keyword"` (швидкий пошук за індексом, за замовчуванням) або `"expanded"` (збагачення запиту через Ollama). |
  | `top` | `Integer` | Ні | Кількість найбільш релевантних результатів (Top-K). За замовчуванням `5` (максимум `100`). |
* **Тіло відповіді (JSON Object)**:
  | Поле | Тип | Опис |
  |---|---|---|
  | `results` | `Array<SearchResult>` | Список знайдених документів, відсортованих за спаданням релевантності (score). |
  | `time_ms` | `Long` | Час обробки запиту сервером у мілісекундах. |
  | `synonyms` | `Array<String>` | *(Опціональне)* Список термінів-синонімів, згенерованих LLM (лише для режиму `expanded`). |

* **Структура об'єкта `SearchResult`**:
  | Поле | Тип | Опис |
  |---|---|---|
  | `doc_id` | `String` | Унікальний ідентифікатор документа (наприклад, `parent_asin` товару). |
  | `score` | `Double` | Обчислений бал релевантності документа відносно термінів запиту. |
  | `snippet` | `String` | Заголовок товару або короткий текстовий фрагмент документа. |
  | `raw` | `Object` | *(Опціональне)* Повний вихідний JSON-документ, вичитаний напряму з диска за байтовим зміщенням. |

### WebSocket API

Ендпоінт: `ws://localhost:8080/ws/search`

Призначений для асинхронного стрімінгу проміжних етапів обробки пошукового запиту в реальному часі.

#### Формат вхідного повідомлення від клієнта (JSON Object)

| Поле | Тип | Обов'язкове | Опис |
|---|---|:---:|---|
| `query` | `String` | Так | Текст пошукового запиту. |
| `mode` | `String` | Ні | Режим пошуку: `"keyword"` або `"expanded"` (за замовчуванням). |
| `top` | `Integer` | Ні | Кількість повертаних Top-K результатів (за замовчуванням `5`). |

Приклад запиту клієнта:
```json
{"query": "vitamin c supplements", "mode": "expanded", "top": 5}
```

#### Повідомлення сервера (JSON, по одному на кожен етап)

1. **Етап 1: Query Expansion (розширення запиту через LLM)**  
   *(У режимі `mode="keyword"` цей етап автоматично пропускається)*:
   * **Поля повідомлення**:
     | Поле | Тип | Опис |
     |---|---|---|
     | `stage` | `String` | Фіксований рядок `"query_expansion"`. |
     | `data.original` | `String` | Оригінальний текст запиту клієнта. |
     | `data.expanded_terms` | `Array<String>` | Список згенерованих мовною моделлю комерційних синонімів. |
   * **Приклад**:
     ```json
     {
       "stage": "query_expansion",
       "data": {
         "original": "vitamin c supplements",
         "expanded_terms": ["ascorbic", "immune", "capsules", "antioxidant"]
       }
     }
     ```

2. **Етап 2: Keyword Search (пошук в інвертованому індексі)**:
   * **Поля повідомлення**:
     | Поле | Тип | Опис |
     |---|---|---|
     | `stage` | `String` | Фіксований рядок `"keyword_search"`. |
     | `data.results` | `Array<SearchResult>` | Список знайдених документів (поля `doc_id`, `score`, `snippet`, `raw`). |
     | `data.time_ms` | `Long` | Час виконання пошуку в індексі у мілісекундах. |
   * **Приклад**:
     ```json
     {
       "stage": "keyword_search",
       "data": {
         "results": [
           {
             "doc_id": "B07XYZ123",
             "score": 18.45,
             "snippet": "Nature Made Vitamin C 1000 mg Tablets...",
             "raw": { ... }
           }
         ],
         "time_ms": 6.8
       }
     }
     ```

3. **Етап 3: Завершення пайплайну**:
   * **Поля повідомлення**:
     | Поле | Тип | Опис |
     |---|---|---|
     | `stage` | `String` | Фіксований рядок `"done"`. Сигналізує клієнту про завершення сесії пошуку. |
   * **Приклад**:
     ```json
     {
       "stage": "done"
     }
     ```

## Дослідження масштабованості та бенчмаркінг

Усі скрипти бенчмаркінгу розташовані в директорії `benchmarks/`.

### 1. Дослідження часу побудови індексу від кількості потоків

Скрипт `cli-client/index.py` виконує серію запусків індексації при різній кількості потоків та фіксує результати в CSV-файл:

```bash
python cli-client/index.py --benchmark 1 2 4 8 12 16 32 --output benchmarks/results/index_speedup.csv
```

Для побудови графіків часу побудови та коефіцієнта прискорення ($S_p = T_1 / T_p$):

```bash
python benchmarks/plot_index_speedup.py --csv benchmarks/results/index_speedup.csv --output docs/benchmarks/index_speedup.png
```

Скрипт генерує два графіки:
- `docs/benchmarks/index_build_time.png` — абсолютний час виконання у секундах;
- `docs/benchmarks/index_speedup.png` — графік фактичного прискорення порівняно з ідеальним лінійним прискоренням.

### 2. Навантажувальне тестування пошукового API

Автономний скрипт `benchmarks/benchmark_search.py` імітує паралельні клієнтські запити:

```bash
# Тест режиму keyword:
python benchmarks/benchmark_search.py --mode keyword --clients 1 5 10 20 30 50 75 100 --duration 10 --output-csv benchmarks/results/search_keyword.csv --output-plot docs/benchmarks/search_throughput.png

# Тест режиму expanded:
python benchmarks/benchmark_search.py --mode expanded --clients 1 2 4 8 --duration 15 --output-csv benchmarks/results/search_expanded.csv
```

Скрипт вимірює:
- Пропускну здатність системи (Requests Per Second, RPS);
- Середню затримку (Average Latency) та перцентилі P50, P95, P99;
- Кількість помилок.

Графіки зберігаються у:
- `docs/benchmarks/search_throughput.png` (RPS vs Concurrency);
- `docs/benchmarks/search_latency.png` (Average and P95 Latency vs Concurrency).

### 3. Навантажувальне тестування через Locust

Для інтерактивного тестування під навантаженням використовується Locust:

```bash
locust -f benchmarks/locustfile.py --host http://localhost:8080
```

Після запуску відкрийте браузер за адресою `http://localhost:8089`.

Також доступний консольний headless-режим:

```bash
# Тест режиму keyword:
locust -f benchmarks/locustfile.py --headless --users 200 --spawn-rate 20 --run-time 60s --host http://localhost:8080 --mode keyword

# Тест режиму expanded:
locust -f benchmarks/locustfile.py --headless --users 10 --spawn-rate 2 --run-time 60s --host http://localhost:8080 --mode expanded
```
